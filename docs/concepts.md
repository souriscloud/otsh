# The basics — terminals, escapes, and SSH

This page is for the reader who has never written a terminal UI and has no
particular reason to know what an "escape sequence" is, what "raw mode"
means, or why an SSH connection is more than a fancy `telnet`. If that's you,
read this before [getting started](getting-started.md) — the rest of these
docs assume you already have this picture in your head. If you've written a
curses app, a `bubbletea`/`wish` app in Go, or anything that pokes `termios`
directly, most of this will be familiar and you can skim for the parts
specific to `otsh`.

Nothing here is otsh-specific until the last two sections. The first four
sections are just how terminals and SSH work, full stop — true whether or not
you ever touch this library.

## A terminal is two byte streams and a grid of cells

Strip away forty years of terminology and a terminal is a small, almost
embarrassingly simple machine: it keeps a grid of character cells (say, 80
columns by 24 rows), it reads bytes arriving from a program and turns most of
them into "put this character in the current cell and move right," and it
sends the bytes you type back to that program. That's the whole contract:
two byte streams, one grid.

Two directions worth naming separately, because it's easy to blur them:

- **Output** — bytes the *program* sends, which the terminal reads and turns
  into changes to the grid: which character sits in which cell, and how it's
  styled.
- **Input** — bytes the *terminal* sends back, generated by whatever you do
  at the keyboard (and, if enabled, the mouse). An ordinary letter key sends
  its own byte. Arrow keys, function keys and modified keys send short,
  fixed sequences of bytes — there's no separate "key event" channel; it's
  the same stream, just more bytes per keystroke.

A little history, because the names everywhere come from it and it's worth
knowing why they're shaped the way they are. In the 1970s, a "terminal" was a
physical box wired to a mainframe or minicomputer: a keyboard, a screen (or,
earlier, a roll of paper — hence "tty," teletypewriter), and a serial cable.
Digital Equipment Corporation's VT100 (1978) is the terminal whose control
language won: cursor movement, colour, clearing — the sequences it defined
are still what a modern terminal understands, extended over the decades
(256-color and true-color support, mouse reporting, bracketed paste) but
never really replaced. When you open Terminal.app, iTerm2, GNOME Terminal,
Windows Terminal, or connect with `ssh`, none of it talks to a physical VT100
— it's all software now — but every one of them still speaks that VT100-
descended language, because that's what decades of programs (`vim`, `top`,
`tmux`, and now every `otsh` app) were written to emit and expect.

The other half of "terminal" is the thing that isn't a screen at all: the
operating system's pseudo-terminal (**pty**) machinery, which is what makes
`ssh`, `tmux`, and a GUI terminal emulator's shell tab possible without a
physical serial port. A pty is a kernel-provided pair of connected file
descriptors — conventionally called the *master* and the *slave* — that
behaves like a real serial line to whatever program is attached to the slave
end. Your shell doesn't know or care whether it's talking to a physical VT100
over a wire or to a pty whose master end is a GUI window's rendering loop; the
byte-stream contract is identical either way. Keep that word in mind — the
whole trick this project is built on, covered a few sections down, is what
happens when there's genuinely no pty on one end at all.

Inside the terminal, interpreting that incoming byte stream is a small state
machine. Most bytes are in "normal" mode: print the byte's character at the
cursor, advance the cursor. But some bytes are special. The byte `0x1b`
(**ESC**) tells the state machine "the next several bytes are not text —
they're an instruction," and it switches into parsing that instruction
instead of printing anything, until the instruction ends. That's the whole
mechanism behind every cursor move, every colour, and the alternate-screen
switch `otsh` uses to leave your scrollback untouched. The next section shows
what those instructions actually look like.

## Escape sequences: bytes that say "do something," not "print something"

The overwhelmingly common family of escape sequence is the **CSI** — Control
Sequence Introducer — which starts with `ESC [` (bytes `0x1b 0x5b`, written
`\033[` in a POSIX shell's `printf`, or `\x1b[` in Odin) and is followed by
zero or more numeric parameters separated by `;`, then a single letter that
names the operation. In shorthand: `ESC [ params letter`. The letter decides
what the parameters mean — there's no way to know what a CSI sequence does
without looking at its final byte.

You don't need a library to produce these — they're just bytes, and `printf`
can write bytes. Each demo below is plain POSIX shell; paste any of them into
a terminal (not a plain log file or a non-terminal pipe — the bytes only mean
anything to something that's actually interpreting them as a terminal would).

**Move the cursor.** The final letter `H` is Cursor Position; its two
parameters are row and column, both **1-indexed**, in that order:

```sh
printf '\033[10;5Hhello, terminal\n'
```

This jumps to row 10, column 5, and writes `hello, terminal` starting there
— wherever your cursor happened to be before this line ran, the text lands
at that fixed spot instead.

**Colour and style.** These are CSI sequences too, just with the final letter
`m` — the family is called **SGR**, Select Graphic Rendition. Each numeric
parameter turns on one attribute: `1` is bold, `32` is a green foreground,
and `0` resets everything back to the terminal's own defaults:

```sh
printf '\033[1;32mgreen and bold\033[0m — back to normal\n'
```

Everything after the first escape sequence is green and bold until the `\033[0m`
resets it — SGR state persists across ordinary characters, even across
newlines, until something turns it off. Forgetting the reset is a classic bug:
the color leaks into whatever the terminal prints next, including your next
shell prompt.

**Clear the screen and go home.** `2J` erases the whole screen (the `2`
selects "entire screen" out of a few erase-scope options); `H` with no
parameters means "row 1, column 1" — home:

```sh
printf '\033[2J\033[H'
```

Two sequences back to back, no text in between, is completely ordinary — this
exact pair is close to what a full-screen program sends once at startup. (Not
literally what `otsh` sends, though: it uses a related but different pair,
covered below.)

**Hide and show the cursor.** Prefixing the parameter with `?` switches into
a different family — a "private mode" — rather than the numbered erase/style
codes above; `?25` is the cursor's visibility, and `l`/`h` are "reset" and
"set":

```sh
printf '\033[?25l'; sleep 1; printf '\033[?25h'
```

The cursor disappears, then reappears a second later. A full-screen app hides
the cursor while it's repainting so you don't see it jump around mid-frame,
then shows it again over an input field on the frames where that makes
sense.

Those four sequences — cursor position, SGR, screen erase, and a private
mode toggle — are most of what a terminal UI actually needs; everything else
is more of the same shape with a different final letter. `otsh`'s renderer
builds on exactly this and nothing more: `tui.run` enters an *alternate*
screen buffer (a fifth private mode, `?1049`, which is why your normal
scrollback is untouched when an `otsh` app quits) and hides the cursor with
precisely the sequences you just ran by hand — see "Terminal setup and
teardown" in [`tui.md`](tui.md) for the exact bytes `run` sends on entry and
reverses on exit. `Style`, `ansi()` and `rgb()` in [`api-tui.md`](api-tui.md)
are a typed wrapper around SGR parameters so your app never builds a raw CSI
string itself — see [Style and color](tui.md#style-and-color).

## Raw mode vs canonical mode — and whose job it is

None of the demos above needed a special mode. But so far every example has
been *output* — bytes the program sends. Input has a wrinkle output doesn't:
by default, the operating system's tty layer does substantial work on your
keystrokes before your program ever sees them, and a full-screen app needs
all of that turned off.

A terminal's default input mode is called **canonical** (or "cooked") mode.
Three things it does that matter here:

- **Line buffering.** The kernel holds your keystrokes in a line buffer and
  hands them to the reading program only once you press Enter — which is
  what makes backspace "work" before you commit a line: you're editing the
  kernel's buffer, not anything your program has seen yet.
- **Echo.** The kernel writes back what you typed so you can see it, entirely
  independent of the program you're running.
- **Signal generation.** Ctrl+C doesn't arrive as the byte `0x03` at all in
  this mode — the kernel intercepts it and delivers `SIGINT` to the
  foreground process group instead. Ctrl+Z similarly becomes `SIGTSTP`.

All three are exactly what you want from a shell prompt and exactly wrong for
a full-screen app. A TUI needs every keystroke the instant it arrives (an
arrow key is several bytes that must be read as they come, not reassembled
after Enter); it draws its own screen, so kernel echo would print your
keystrokes a second time in the wrong place; and it usually wants to decide
what Ctrl+C means itself (see [cookbook.md §12](cookbook.md#12-graceful-exit)
for how `otsh` apps handle it as an ordinary keypress).

**Raw mode** is canonical mode's opposite: line buffering off, echo off,
signal generation off, so bytes reach the program one at a time, unmodified,
un-echoed, un-intercepted. Concretely, on POSIX this means clearing a
specific set of `termios` flags. `tui/local.odin:local_enter_raw` does
exactly this, for the one situation in this codebase where it's needed — see
below:

<!-- check:verbatim tui/local.odin -->
```odin
raw.c_iflag -= {.BRKINT, .ICRNL, .INPCK, .ISTRIP, .IXON}
raw.c_oflag -= {.OPOST}
raw.c_lflag -= {.ECHO, .ICANON, .IEXTEN, .ISIG}
raw.c_cflag += {.CS8}
raw.c_cc[.VMIN] = 0
raw.c_cc[.VTIME] = 0
```

`ECHO` is the kernel-echo bit, `ICANON` is line buffering, and `ISIG` is
signal generation — the three things called out above, turned off in one
place. (The rest are smaller POSIX details — input parity/stripping,
output post-processing, 8-bit character size, and non-blocking read
timing — that matter for a fully correct raw mode but aren't the concept
here.)

**Now the part specific to `otsh`: on this project, raw mode is never the
server's job.** When your `ssh` client connects and asks for a pty (more on
that request in the next section), *your local terminal* — the one you're
typing into — is what goes into raw mode, and your local `ssh` client does
that to itself, the same way any full-screen program run directly in your
terminal would. The `otsh` server, running on some other machine, never has
a local tty to configure in the first place — there's nothing for it to run
`tcsetattr` against. The one place this codebase's server side *could* need
raw mode and deliberately doesn't is the entire point of the next two
sections; the README's ["The trick"](../README.md) section and
architecture.md's ["The central idea: no pty, no
shell"](architecture.md#the-central-idea-no-pty-no-shell) are the full
explanation and the authority on it — this page won't repeat it, only set up
why it's surprising.

The one place raw mode *does* happen inside this codebase is
`tui/local.odin`, quoted above — used only when an app runs with no SSH
involved at all (`sshtui.run_local`, or the local backend directly, covered
in [tui.md](tui.md#local-terminal-use-without-ssh)). There, this process's
own stdin genuinely is a local tty, and genuinely does need to be put in raw
mode by somebody — and there's no SSH client standing in front of it to have
done that job already.

## What SSH actually gives you

Set terminals aside for a moment. SSH (the protocol `ssh`/`sshd` speak, and
what `otsh:libssh` binds and `otsh:ssh` builds on) is, underneath the parts
most people know it for, two things stacked on each other:

1. **An encrypted, authenticated transport.** A key exchange establishes a
   shared secret and proves the server holds the private half of its host
   key; everything after that is encrypted and integrity-checked. This is
   the layer `otsh`'s [security model](security.md) mostly concerns itself
   with — key exchange algorithms, ciphers, MACs, host key management.
2. **Multiplexed channels running over that transport.** A single encrypted
   TCP connection can carry several independent, flow-controlled data
   streams — *channels* — opened and closed while the connection stays up.
   This is what lets one `ssh` connection forward a port, run a command,
   *and* carry an interactive session simultaneously if it wants to; `otsh`
   only ever deals with one channel per connection, opened for an
   interactive session.

Channels are defined in [RFC 4254](https://www.rfc-editor.org/rfc/rfc4254),
"The Secure Shell (SSH) Connection Protocol" — §5 covers the channel
mechanism itself (opening, data transfer, closing), and §5.4 defines
**channel requests**: `SSH_MSG_CHANNEL_REQUEST` messages that ask the far end
to do something with an already-open channel, distinct from opening or
closing it. An interactive session (§6.1, "Opening a Session") is a channel
that, by convention, sees three of these requests in order, each one a
question the server can accept or refuse independently:

- **`pty-req`** (RFC 4254 §6.2) — "I'd like a pseudo-terminal for this
  channel; here's `$TERM`, and here's my window size in characters (and,
  optionally, pixels)."
- **`shell`** (RFC 4254 §6.5) — "Now start the default interactive shell (or,
  via a sibling request the same section defines, `exec` a specific
  command)."
- **`window-change`** (RFC 4254 §6.7) — sent later, any time the client's
  terminal is resized, carrying the new dimensions.

Here's the detail that makes `otsh` possible: **nothing in the protocol
requires the server to actually allocate a pseudo-terminal to answer
`pty-req` with success.** The request is "would you set this up for me,"
not "prove to me afterwards that a specific kernel object exists." A normal
`sshd` answers by calling out to the OS pty machinery from the terminal
history section above — allocating a real master/slave pty pair and forking
the user's login shell onto the slave end, because that's what makes a
Unix login shell work over SSH. But an SSH server answering on behalf of a
program that has no shell to fork, and no OS pty to allocate — a program
that *is itself* something that draws a screen and reads keystrokes — can
answer "yes, noted" to `pty-req`, record the geometry it was told, and
allocate nothing whatsoever. The client has no way to tell the difference:
its own terminal already went into raw mode locally (previous section) the
moment *it* decided to send `pty-req`, entirely independent of how the
server answers.

## The channel is the terminal

Once a server has taken that path — answering `pty-req` and `shell`
successfully without a real pty behind either — something falls out of it
that's worth stating plainly, because it's the central idea this whole
library rests on: **the channel itself has become the terminal.** Not a
pipe *to* a terminal, not a description *of* a terminal — the channel's own
data stream *is* the same two-byte-streams-and-a-grid contract from the
first section, with the SSH channel standing in for the wire a physical
VT100 would have used:

- Bytes the client sends down the channel are keystrokes — exactly the input
  half of the first section, just arriving over an encrypted multiplexed
  channel instead of a serial cable or a local pty.
- Bytes the server writes to the channel are read by the *client's own*
  terminal emulator and interpreted exactly like the escape sequences from
  the second section — cursor moves, colour, the alternate screen. The
  server doesn't need a terminal emulator of its own; it only needs to know
  what to emit, the same knowledge the shell demos above exercised by hand.
- A `window-change` request is this protocol's equivalent of `SIGWINCH` — the
  Unix signal a real pty would normally deliver when its window resizes.
  There's no pty to deliver a `SIGWINCH` from here, so the channel request
  *is* the resize notification, carrying the new dimensions directly instead
  of merely prompting an `ioctl` to go read them.

This is exactly what `ssh/server.odin:cb_pty_request` does — record the
geometry, allocate nothing — and it's why the very last section of
architecture.md's central-idea discussion can say, correctly, that grepping
the `ssh` and `sshtui` packages for `tcsetattr` or `termios` finds nothing:
there is no local tty on that side of the connection for either call to act
on. Full detail — the exact callback, the connection lifecycle around it,
and the reasoning for refusing `exec`/`subsystem` requests instead of
answering them too — lives in architecture.md's ["The central idea: no pty,
no shell"](architecture.md#the-central-idea-no-pty-no-shell); this section
exists to make sure you can *derive* why that works from what a terminal and
an SSH channel actually are, not just take it as a given.

One consequence worth being explicit about, because it resolves a question
that otherwise nags: if the server never allocates a pty and never touches
termios, how does it decode arrow keys, mouse events, and Ctrl+C from the
raw bytes arriving on the channel? The same way *any* terminal-facing program
would — by parsing the byte stream itself. That parser is `tui`'s job
(`parse_input` in [api-tui.md](api-tui.md#parse-input)), and it's the same
parsing a local, non-SSH `tui` app needs, because the bytes look identical
either way. That's the seam the next section is about.

## Model, update, view: the shape every otsh app has

Everything above is background that would be true of any program that draws
a terminal UI, over SSH or not. This section is where it turns into
`otsh:tui`'s actual API — the types below are exactly as declared in
`tui/tui.odin`; see [api-tui.md](api-tui.md) for the complete reference.

An `otsh` app is a `Model` (any struct you define, holding whatever state
your app needs) plus three procedures wired together by an `App` value:

<!-- check:verbatim tui/tui.odin -->
```odin
App :: struct {
	data:   rawptr,
	init:   proc(p: ^Program),
	update: proc(p: ^Program, msg: Msg),
	view:   proc(p: ^Program, s: ^Screen),
}
```

`data` is your `Model`, stored as an untyped pointer and cast back at the top
of `update`/`view` (`m := (^Model)(p.app.data)` — see the worked examples in
[getting-started.md](getting-started.md#writing-your-first-app)). `update`
runs once per incoming message; `view` runs once per frame and must paint a
**complete** picture — every visible cell, every time, with no separate
"erase" step. That's a deliberate constraint, not an oversight: because
`view` always describes the *whole* current frame rather than a patch onto
the previous one, there is no stale content left over from three frames ago
for you to track down — the cost of a wrong pixel is a bug in *this* frame's
`view`, never a leftover from an earlier one. [tui.md](tui.md#the-model) has
the longer case for why this is worth the apparent wastefulness.

"Every message `update` can receive" is a closed set — a tagged union with
exactly four cases:

<!-- check:verbatim tui/tui.odin -->
```odin
Msg :: union {
	Key,
	Mouse,
	Resize,
	Tick,
}
```

`Key` and `Mouse` are decoded input — the same bytes-in-a-stream problem from
the SSH section above, parsed by `tui`'s own input decoder into a typed
event, documented field by field in [api-tui.md](api-tui.md#key) and
[api-tui.md](api-tui.md#mouse). `Resize` carries the new geometry whenever
the terminal's dimensions change — over SSH, that is a `window-change`
channel request from two sections ago, translated into the exact same
message a locally-resized terminal window would produce; your `update`
never needs to know which one happened. `Tick` fires once per frame with
`dt`, the real elapsed seconds since the previous one — drive animation off
`dt`, never off a frame counter, since nothing guarantees the loop hits its
target rate every tick (see [cookbook.md §6](cookbook.md#6-frame-rate-independent-animation)
for exactly why that goes wrong).

The part that turns "paint everything, every frame" from wasteful into
cheap happens one layer below `view`, and you never call it yourself: after
`view` returns, `flush` walks the frame you just painted against the one
actually last sent to the terminal, cell by cell, and emits only the escape
sequences needed to reconcile the two — the same CSI/SGR vocabulary from the
second section, generated for you instead of hand-written. Measured in the
README on a 100×30 session: first paint 6.3 KB, idle throughput about
530 B/s, one keypress about 230 B — because an unchanged cell costs nothing
to redraw, only a changed one costs bytes on the wire. `view` gets to be
simple (repaint everything) precisely because something else made "repaint
everything" cheap.

Wiring this loop up to a real backend — local terminal or SSH channel — is
`sshtui`'s job, not `tui`'s, and it's worth naming its two public entry
points here since they're where this model actually starts running:
`sshtui.serve` (documented in [api-sshtui.md](api-sshtui.md#serve)) runs one
`tui.Program` per accepted connection, handing your `create` a
[`sshtui.Info`](api-sshtui.md#info) — the client's `$TERM`, negotiated
window size, and (if you've configured `identity_secret`) a stable
pseudonymous `id` derived from their SSH key, explained in full in
[security.md](security.md#4-pseudonymous-identity). `sshtui.run_local`
(documented in [api-sshtui.md](api-sshtui.md#run-local)) runs the identical
`App` against your own terminal instead, which is what makes a `--local`
development flag possible at all — see
[getting-started.md](getting-started.md#the---local-development-loop).

## How the four packages stack

Four packages, and the boundary between them is exactly the boundary this
page has been drawing all along — the byte-stream-and-grid model on one
side, the SSH transport on the other, meeting only where something has to
adapt one to the other:

```text
                     your app (create / update / view)
                     /                              \
              sshtui.serve                     tui.run_local
                     |                                |
              ssh.serve                    tui (Program, Screen,
              (Session, read/write)         input parser, diff renderer)
                     |
              libssh (C, via foreign import)
```

`tui` — the package the whole previous section was about — never imports
`ssh` or `sshtui`; it only knows about an abstract `Backend`, a struct of
three closures standing in for wherever the bytes actually come from and go
to:

<!-- check:verbatim tui/tui.odin -->
```odin
Backend :: struct {
	data:  rawptr,
	write: proc(data: rawptr, buf: []u8) -> int,
	poll:  proc(data: rawptr, buf: []u8, timeout_ms: int) -> (n: int, ok: bool),
	size:  proc(data: rawptr) -> (cols, rows: int),
}
```

`ssh` implements the SSH side of that story and never imports `tui` either —
it's a general-purpose server that hands a caller a `Session` to read and
write bytes on; nothing in it knows what a `Screen` or a `Cell` is, and it
could serve a line-oriented protocol just as easily as a TUI. `sshtui` is
the only package that imports both: it wraps an `ssh.Session`'s
read/write/size as a `tui.Backend` (satisfying exactly the three closures
above) and drives `tui.run` with it, once per connection. `tui/local.odin`
supplies the *other* implementation of that same `Backend` shape, backed by
your own stdin/stdout/`termios` instead of a channel — which is what makes
`sshtui.run_local` able to run the identical `App` with no SSH involved at
all. Neither backend is privileged; `tui.Program` only ever calls through
the struct, so it never learns which one it's driving. `libssh` is the
bottom layer neither `tui` nor `sshtui` touches directly: `otsh:libssh` is
Odin bindings against your system's libssh, and `ssh/server.odin` is the
only package that imports it.

The full version of this diagram, with `libssh` binding details and the
file-by-file import boundaries spelled out, is architecture.md's
["Layering"](architecture.md#layering) section — the authority on this if
anything here seems to conflict.
